#+TITLE: meta-common — Shared Build Infrastructure
#+STARTUP: showall

Common Makefile, Lisp build scripts, and shell tooling shared across
=cogen-meta=, =IDEAS=, and =render-stack-meta= projects.

* Quick Start

Add as a git submodule at =.cl-make/=:

#+begin_src bash
git submodule add git@github.com:jolby/meta-common.git .cl-make
git submodule update --init
#+end_src

For a minimal project Makefile:

#+begin_src makefile
PROJECT_SYSTEM := my-project
include .cl-make/cl-project.mk
#+end_src

That's it — you get =load=, =test=, =clean=, =fresh-build=, and more.

* Makefile System (~cl-project.mk~)

The centerpiece of =meta-common=. A GNU Make include that provides
a standardized development workflow for any Common Lisp project.

** Setup

Include =cl-project.mk= after setting =PROJECT_SYSTEM= (the bare minimum):

#+begin_src makefile
PROJECT_SYSTEM := my-project
include .cl-make/cl-project.mk
#+end_src

Full example with all overrides:

#+begin_src makefile
PROJECT_SYSTEM := my-project
TEST_SYSTEM := my-project/tests            # default: PROJECT_SYSTEM/tests
DYNAMIC_SPACE_SIZE := 8096                  # default: 4096 (MB)
CLEAN_EXTRA_PATTERNS := *.db *.db-journal  # extra globs for make clean
EXTRA_ASDF_DIRS := ../vendor/some-lib/     # additional ASDF registry dirs
EXTRA_ASDF_TREES := ../dev/                # additional :tree source registry entries
GOLDEN_PACKAGE := my-project.test           # enables generate-goldens target
BINARY_NAME := my-cli                       # enables build/install targets
ASDF_SOURCE_REGISTRY := no                 # skip slow :tree scan (use Quicklisp-only)
include .cl-make/cl-project.mk

# Project-specific targets go here
demo: check-quicklisp
	$(SBCL_QL) --eval '(my-project.demo:run)'
#+end_src

** Compiler-Warning Lint — =make lint= (bd-a8r, bd-twd)

A docstring that quotes a phrase with a plain double quote ENDS at that quote.
The rest of the sentence becomes body forms, so the function still compiles and
signals only the first time it runs. Parenthesis checkers, CST parsers and
structural editors all accept such a file; the compiler's own
"undefined variable" warning is the only cheap detector, so =make lint= greps
the compile log for it and fails if it is attributed to a file under one of the
directories in =$(LINT_SOURCE_DIRS)= (default =src=).

** What =make lint= scans is TWO decisions, not one (bd-lnz)

By default lint compiles =$(PROJECT_SYSTEM)= and reports hits under =src/=. A
project's rig and its test system are ASDF systems in their own right —
siblings of =$(PROJECT_SYSTEM)=, not components of it — so nothing compiles
them and a docstring trap in =rig/= or =test/= is invisible. Two variables
close that gap, and a project needs BOTH halves:

| Variable                | Default              | Meaning |
|-------------------------+----------------------+---------|
| =LINT_SOURCE_DIRS=      | =src=                | Directories a hit is reported from. Whitespace-separated; a hit under ANY of them fails the target. This is the canonical name |
| =LINT_EXTRA_SYSTEMS=    | /empty/              | Extra ASDF systems to force-load before grepping, e.g. =my-project/rig my-project/test=. A directory only gets checked if some loaded system compiles it |

#+begin_src make
LINT_SOURCE_DIRS   := src rig test
LINT_EXTRA_SYSTEMS := my-project/rig my-project/test
#+end_src

Widening only the filter changes nothing (the files are never compiled), and
naming only the extra system compiles the trap and then discards the evidence.
Both are cheap to get wrong in a way that still reads as a pass, which is why
=make lint-trust='s fourth fixture runs the pair in both directions: the trap in
the test system is RED and names =test/trap2.lisp=, and the same fixture with
the filter narrowed back to =src= is GREEN while the warning is still in the
log.

=LINT_SOURCE_DIR= (singular) is the original spelling. It is still honoured,
but only when =LINT_SOURCE_DIRS= is unset, so it now means "this one
directory" rather than "the whole scope". New work should use the plural.

The failure mode is the force-load, not the grep. If the load stops at file N,
every file after N is unlinted and "no warnings found" is a lie by omission —
which is what happened for two sessions: a GENERATED slot in =limited-box=
warned, ASDF called that a failed compile, and the load died before reaching
the files a Material text-field author edits (bd-twd). So:

- the force-load runs with =:on-failure :warn=. A file that PRODUCED a warning
  is reported and the check continues. This is unconditional: no project would
  declare "my own generated slot warns" as a tolerance, and a detector any
  warning can switch off is not a detector.
- =LOAD_FORCE_EXTRA= is still honoured, so a project's own tolerance applies
  here exactly as in =test= and =load=.
- a load that still fails is FATAL (=:on-failure= downgrades a failed compile,
  never a compile that produced no fasl) and nothing is claimed about the code.
- =make lint-trust= proves all of it on fixture projects: a warning with
  nothing to find is GREEN and says how many files it tolerated; the same
  warning followed by a docstring trap is RED and names the file; the trap
  alone is RED too; and the trap in a separate system under =test/= is RED
  while the same compile with the filter narrowed to =src= is GREEN.

** SBCL Commands

The Makefile provides two SBCL invocation patterns:

- =$(SBCL_RUN)= — Full boot: Quicklisp + ASDF source registry tree scan.
  Use for =load=, =test=, =build=, and =fresh-build= where sibling repo
  discovery matters.  Set =ASDF_SOURCE_REGISTRY=no= to fall back to
  Quicklisp-only (1-2s startup vs 15s+).

- =$(SBCL_QL)= — Lightweight: Quicklisp only, no ASDF source registry.
  Use for =demo-%/= targets, fast dev cycles, or any target that just
  needs =ql:quickload=.  Always ~1-2s startup.

Both respect =SBCL=, =SBCL_HOME=, =QL=, and =DYNAMIC_SPACE_SIZE= overrides.

#+begin_src makefile
# In your project Makefile:
demo-todo: check-quicklisp
	$(SBCL_QL) --eval '(ql:quickload :my-project/demo/todo)' \
	           --eval '(my-project.demo.todo:run-todo-demo)'
#+end_src

** Output Capture (~capture-output~)

The =capture-output= macro wraps any command with timestamped output
capture to a predictable file:

#+begin_example
/tmp/<project>-<target>-LATEST.txt
#+end_example

Usage in project Makefiles:

#+begin_src makefile
demo-todo: check-quicklisp
	$(call capture-output,demo-todo,$(SBCL_QL) \
	  --eval '(ql:quickload :my-project/demo/todo)' \
	  --eval '(my-project.demo.todo:run-todo-demo)')
	@echo "Output: $(OUTPUT_DIR)demo-todo-LATEST.txt"

test-integration: check-quicklisp
	$(call capture-output,test-integration,$(SBCL_RUN) \
	  --eval '(ql:quickload :my-project/integration-tests)' \
	  --eval '(my-project.integration-tests:run)') ; \
	RC=$$?; \
	grep -E "Passed:|Failed:" $(OUTPUT_DIR)test-integration-LATEST.txt | tail -1; \
	exit $$RC
#+end_src

The macro:
- Deletes any previous output file for the same target.
- Writes a timestamped header.
- Captures both stdout and stderr via =tee=.
- Preserves the exit code of the wrapped command (via pipefail).
  Capture it with =RC=$$?= after the =$(call ...)= with a =; \= continuation.

Standard targets =load=, =force-load=, and =test= use =capture-output= internally.
=load-summary= and =test-summary= read from =$(LOAD_OUTPUT)= and =$(TEST_OUTPUT)=,
which are derived from =$(OUTPUT_DIR)=.

** The Load Verdict — four targets, one predicate (bd-t5m)

=make load=, =make fast-load=, =make force-load= and =make fast-force-load=
all end in the same script, =load-verdict.sh=, the way the test targets end in
=test-verdict.sh=.  Before this, four copies of one blind grep decided whether a
load had failed:

#+begin_src sh
  grep -qE "caught (fatal )?(ERROR|WARNING)" <log>
#+end_src

That predicate was wrong in both directions, and both were measured before it
was replaced:

- *It could not fail, in =force-load=.*  The recipe grepped =$(LOAD_OUTPUT)=
  (=/tmp/<system>-load-LATEST.txt=), which is the *load* target's log.  It wrote
  =/tmp/<system>-force-load-LATEST.txt=, so the grep was reading a file that need
  not exist; grep exits 2 on that, =if= reads failure, and the gate passed.  A
  system whose docstring ended at an inner quote produced
  =; undefined variable: ...= in force-load's own log and =make force-load=
  still exited 0.
- *It cried wolf.*  =caught WARNING= also matches warnings that are benign for a
  load gate and are not the project's to fix — real logs on this machine contain
  =; caught WARNING: Duplicate definition for G found in one file.= and LOOM's
  =; caught WARNING: LOOM requires the 'if' form to have an 'else' clause.=  The
  documented way to tolerate one is =LOAD_FORCE_EXTRA= (which downgrades ASDF's
  compile-file failure behaviour), and the grep re-failed exactly the projects
  that had used it.

What it gates on now:

- the load command exited non-zero;
- the log was never created, or holds nothing but =capture-output='s header;
- the compiler reported an ERROR, per-condition (=; caught ERROR:=) or counted
  (=; caught 2 fatal ERROR conditions=);
- an undefined *variable or function* in a file under =$(LOAD_SOURCES)=.

Everything else is REPORTED, not gated: benign WARNINGs and STYLE-WARNINGs are
counted and echoed into the log under =warnings tolerated (not a gate)=, so a
reader sees them and a future detector can be added on purpose.  Style-warnings
never gate on their own.

An undefined *function* is gated because of how the log is produced, not by
assumption: the force targets run a plain =ql:quickload= first, so by the time
the forced compile happens every file in the system is loaded.  A name that is
still undefined exists nowhere, and the call would signal =UNDEFINED-FUNCTION=
the first time it ran.  A legal backward reference (file A calling a function
file B defines later) produces no warning at all in this log — measured.

=LOAD_SOURCES= (default =$(PROJECT_DIR)=) is the scope for that check.  Narrow it
to the directories you own if the tree vendors or generates code:

#+begin_src makefile
  LOAD_SOURCES := $(PROJECT_DIR)/src $(PROJECT_DIR)/test
#+end_src

=make load-trust= is the regression test: it runs the real load targets against
three fixture projects and then feeds =load-verdict.sh= synthetic logs taken
verbatim from a real SBCL log.  A project with style-warnings only must PASS,
a project with a real WARNING it declared benign must PASS, and a project with
an undefined variable *and* an undefined function must FAIL and name both files
— on a command exit of 0, so the red cannot be blamed on the exit status.

*Limitation, measured:* =ql:quickload= compiles with Quicklisp's quiet mode, so
=make load= and =make fast-load= logs contain no compile warnings at all when the
system is stale — the verdict can only report what the log shows, which for those
two targets is very little.  =make force-load= and =make fast-force-load= are the
loud ones (ASDF's forced recompile runs outside quickload), and =make lint=
covers the same undefined-symbol class over the directories it is told to scan.

** The Test Verdict — read the verdict line, not the counters

=make test=, =make test-package=, and =make test-eval= do not derive their
result from SBCL's exit status, and they do not trust the
=Passed:/Failed:= counters.  Neither is a test result:

- SBCL exits 0 with failing tests.  =make test= binds Parachute's
  =cl-user::*exit-on-test-failures* to =NIL= on purpose; binding it =T=
  makes Parachute call =sb-ext:exit= from inside =asdf:test-system=, which
  ASDF unwinds into a confusing "compilation unit aborted / caught 1 fatal
  ERROR condition" banner even on a green run.
- Parachute's =Failed:= counter does not count a test that *failed to
  evaluate* (an unhandled error in the test body).  Its =summarize= method
  filters =TEST-RESULT= objects out of the counters, and such a test is one.
  The log then shows =Passed: 361 / Failed: 0=, a =✘= line, and a
  =;; Failures:= block, all at once.

So the shared targets call =test-verdict.sh=, which computes ONE verdict
after the run, writes the reasons (if any) and then the verdict into the
captured log *as its last line*, and exits on that verdict (bd-xvg).
The verdict is the log's own conclusion:

#+begin_example
;; Summary:
Passed:     1
Failed:     0
Skipped:    0

;; Failures:
   0/   0 tests failed in MY-PROJECT/TESTS::SOMETHING
The test failed to evaluate properly:
  ...

=== VERDICT reasons ===
  - the ';; Failures:' block is non-empty (it includes tests that failed to evaluate, which the counters ignore)
  - 1 test(s) failed to evaluate properly
  - the log contains the ✘ failure glyph
=== VERDICT: FAIL (target: test, log: /tmp/my-project-test-LATEST.txt) ===
#+end_example

The gates are: the command's exit status, =^Failed: [1-9]=, a
=;; Failures:= block, the string =failed to evaluate properly=, the =✘=
glyph, and — for =test=/=test-package= — the presence of a summary line at
all.  That last gate is what stops =make test= from reporting success on a
suite that never ran (a system whose =test-op= does nothing exits 0 and
prints no summary).

=make test-trust= is the regression test for all of this.  It runs five
fixture systems in =test-fixtures/= through the real targets and asserts
that a green suite PASSes, that a suite whose only failure is an unevaluated
test FAILs (while its counters still say =Failed: 0=), that a suite
that never ran FAILs too, that a project with no suite says so instead of
failing, and that a suite which does not even COMPILE is red, unjudged and
never receipted (45 checks, ~95 s).  Run it after changing any of this machinery.

*** "A green run must say it judged something" (bd-829)

=make test-trust='s seventh case is the one that keeps this honest, and it came
from two measured failures in one day.  A test file that did not READ made SBCL
abort before =test-verdict.sh= ran: the log ended in a backtrace, `make test`
exited 0, and a GREEN receipt was written for a build that compiled nothing — so
the next identical run answered =cached … PASS=.  Two independent faults, both
fixed, both pinned by a fixture:

- *The no-test-system marker leaked through a backtrace.*  The guard's marker
  (see above) was a literal inside the =--eval= source it hands SBCL, and SBCL
  echoes every =--eval= string in its =PROCESS-EVAL/LOAD-OPTIONS= frame.  So ANY
  fatal error put the marker in the log and the recipe took its "nothing to
  judge, exit 0" branch.  The guard now ASSEMBLES the marker at run time
  (=format t "~&test: NO TEST ~A …" "SYSTEM"), so the phrase exists nowhere in
  the source, and the recipe matches the assembled line anchored at column 0
  (=^…=), where the guard prints it and where a backtrace frame (indented,
  mid-line) cannot.
- *A receipt could be made from a log with no conclusion in it.*
  =gate-receipt.sh= records only what the gate's log says, so a gate declares
  the line a concluded run leaves behind, and a green exit without one is not
  receipted — it FAILS.  This is the part that closes the class: the next
  diagnostic string that leaks into a backtrace cannot become a green receipt.

#+begin_src makefile
# The defaults (only the test targets declare one; a gate may set it to empty)
# $$ is make's escape for one literal $, so grep sees "( |$)".
GATE_REQUIRE_LOG_test         ?= ^(=== VERDICT: PASS|$(NO_TEST_SYSTEM_MARKER)( |$$))
GATE_REQUIRE_LOG_test-package ?= ^=== VERDICT: PASS
GATE_REQUIRE_LOG_test-eval    ?= ^=== VERDICT: PASS
# A project's own gate opts in with the line ITS verdict prints:
GATE_REQUIRE_LOG_demos-dl-parity ?= ^demos-dl-parity: [0-9]+ demo(s), PASS
#+end_src

Two rules when writing one.  *Anchor it with =^=*: a backtrace echoes source
mid-line, so an unanchored substring is satisfied by a crash.  *Ask for the word
=PASS=*, not merely "a verdict line": a log that says =VERDICT: FAIL= beside a 0
exit is exactly the false green one step further out.  The test gate admits its
second honest ending, the no-test-system report, because bd-wf7.1 deliberately
writes no verdict line there.

The pattern is part of the DIGEST, so tightening it after the fact invalidates
the receipts made under the looser one instead of answering from them.

** A project with no test system (bd-wf7)

=make test= force-loads =$(TEST_SYSTEM)= and then runs ASDF's test-op.  In a
project where that system does not exist, the load signalled
=SYSTEM-NOT-FOUND=, nothing ran, and the verdict was =FAIL= with "no test summary
in the log" — a red gate that says nothing about the code and that no change to
the code can ever turn green.  A target nobody can pass is a target everybody
learns to ignore.

So the first form of the recipe ASKS ASDF whether =$(TEST_SYSTEM)= exists.  If it
does not, the target prints three plain sentences, exits 0, and writes **no
verdict line** — because there is no run to judge — and =make test-summary=
repeats that instead of claiming the log is missing:

#+begin_example
test: NO TEST SYSTEM in this repo — my-project/tests does not exist.
      The suite here is `make codegen-test`.
      no assertions were run, so there is nothing to summarize.
#+end_example

The Lisp assembles that first line at run time (="NO TEST ~A"= with the word
supplied as an argument), and the recipe matches it anchored at column 0.  That
is not style: the marker used to be a literal inside the =--eval= source SBCL
was handed, and SBCL echoes every =--eval= string in a backtrace frame, so ANY
fatal error put the marker in the log and the recipe took its "nothing to judge,
exit 0" branch — a broken build reported as green, twice in one day (bd-829).
See the receipts section, "A green run must say it judged something".

| Variable            | Default   | Meaning |
|---------------------+-----------+---------|
| =TEST_ALTERNATIVE=  | /empty/   | The target that DOES run this project's suite, named in that message.  A plain target name: =TEST_ALTERNATIVE := codegen-test= |

ASDF answers authoritatively on purpose.  Grepping the =.asd= files for a
=/tests= system is the tempting shortcut and is wrong: a test system can be
defined in another system's =.asd= (=mcclim-render-stack= defines its whole
family in one file), it need not be spelled =/tests= (=render-parity= uses
=/test=), and it can be found through the source registry rather than in the
project directory.  =make test-trust='s sixth case pins all of it: a fixture
with no suite must exit 0, name the missing system, point at
=TEST_ALTERNATIVE=, carry no verdict line, and not be described by
=test-summary= as a log that does not exist.

/If your project defines its own =test:= target, none of the above applies to
it./  Either call =test-verdict.sh= yourself at the end of the recipe, or do
not override =test:= at all.


** Targeted Testing

Run individual test packages or arbitrary test forms without running the
full test suite.  Both targets load =$(PROJECT_SYSTEM)= before
=$(TEST_SYSTEM)= (matching the =test= target), so test code is always
available.

- =make test-package PKG=:my-package= — Run a single Parachute test package.
  Optionally set =REPORT=interactive= for interactive debug mode.
  PKG is passed through as a Parachute designator (package keyword/symbol,
  or a single test/suite name). Package resolution is lenient: if the exact
  name is missing, dots ↔ slashes are swapped and retried, so
  =PKG=:cogen-core.tests= and =PKG=:cogen-core/tests= both resolve the
  `cogen-core/tests` package (ASDF secondary test systems are conventionally
  named =system/tests=). Non-package designators (suite/test symbols like
  =PKG=agent-loop-suite=) pass through unchanged.

- =make test-eval EVAL="(form)"= — Run any test expression.  Works with
  Parachute or any custom test entry point.  /No quoting issues:/ the
  form is written to a temp file via Make's =$(file ...)= and loaded with
  =--load=, completely bypassing shell quoting.  Single quotes, double
  quotes, nested forms — all fine.

  /Not= a way to judge an unsupported framework: =test-eval= deliberately does
  not require a test summary (it runs an arbitrary form), so a framework whose
  report =test-verdict.sh= cannot read will look green here even when its suite
  failed.  FiveAM is exactly that case (bd-phe); a real suite belongs in
  =make test= or =make test-package=, which do require a Parachute summary.

#+begin_src makefile
# Run a specific test package:
make test-package PKG=:my-project.test.smoke

# Same, with Parachute's interactive debugger:
make test-package PKG=:my-project.test.smoke REPORT=interactive

# Run a full package via test-eval (same as test-package above):
make test-eval EVAL="(parachute:test :my-project.test)"

# A custom entry point with quoted symbols and strings:
make test-eval EVAL="(my-tests:run-single 'test-foo :verbose t)"
make test-eval EVAL='(format t "hello world")'
#+end_src

Output is captured to =/tmp/<project>-test-package-LATEST.txt= or
=/tmp/<project>-test-eval-LATEST.txt= respectively.

/Note:/ =test-eval= writes the form to a temp file at
=$(TEST_EVAL_TMP)= before loading it.  The =$(file ...)= function
bypasses all shell quoting issues — no escaping needed for single quotes,
double quotes, or nested forms.

** Gate Receipts — a gate whose inputs did not change does not run

=make test=, =make test-package=, and =make test-eval= are /receipted/.  A
receipt records one GREEN run against a digest of the gate's inputs; a later
run with the same digest restores =(OUTPUT_DIR)<target>-LATEST.txt= and the
verdict instead of executing anything.

#+begin_example
$ make test
... Passed: 5336 / Failed: 0 ...
test: receipt 1e214da7 written (green, 61.2s) — log: /tmp/stratodendron-test-LATEST.txt

$ make test
test: cached (61.2s, 1e214da7) — log: /tmp/stratodendron-test-LATEST.txt
  === VERDICT: PASS (target: test, log: /tmp/stratodendron-test-LATEST.txt) ===
$ make test-summary          # reads the restored log, as always
#+end_example

The invariants, each of which is worse to break than to be slow:

1. *A false hit is worse than a slow miss.*  When in doubt the input is in the
   digest: the whole project, every sibling repo with an =.asd= (ASDF loads
   them through =( :tree PARENT_DIR)=), the SBCL binary and its =--version=,
   the Quicklisp dist, =ASDF_SOURCE_REGISTRY=, =SBCL_HOME=, and the variant of
   the run (=PKG=, =EVAL=, =REPORT=).
2. *Only green is receipted.*  A red gate always runs again, so a receipt can
   never turn a red gate green.
3. *The inspection surface survives.*  A hit restores the log byte-for-byte
   and prints where it is.  Never re-run a gate to look at its output.
4. *The receipt records the target's verdict.*  The wrapper wraps the whole
   =<gate>-uncached= target, so =make test='s own exit status (which comes
   from the verdict, not from SBCL) is what is recorded.
5. *The cache is machine-local derived state*, =$(PROJECT_DIR)/.gate-cache/=,
   gitignored, never committed.
6. *A green gate must say it judged something.*  A gate that declares what its
   conclusion line looks like (=GATE_REQUIRE_LOG_<gate>=, below) is not
   receipted when its log holds no such line: it fails instead.  Exit status is
   not evidence — the log is.  Added after a compile error in =make test= was
   receipted green twice in one day (bd-829).

Why the recipe is duplicated: each cached gate keeps its exact previous recipe
under =<gate>-uncached= and gains a one-line wrapper.  On a miss the target
behaves exactly as it did before receipts existed — same capture, same log,
same verdict — so adopting receipts cannot change a result through a changed
recipe.  =test-uncached=, =test-package-uncached= and =test-eval-uncached= are
make targets in their own right; run them if you want to bypass the receipt
layer entirely.

Everyday commands:

#+begin_src sh
make cache-status            # what is cached, where each log lives
make cache-status VERBOSE=1  # + receipt count and manifest path per gate
make FORCE=1 test            # run despite a matching receipt
make cache-clean             # drop every receipt (or GATE=test for one)
make gate-selftest           # the tool's own 35 assertions, ~2s, no SBCL
make test-receipts           # end-to-end wiring check through the fixtures
#+end_src

Digest inputs, and the traps that must stay handled:

- =build-info.sexp= is regenerated by *every* make run.  It is excluded; if it
  were an input, no receipt would ever hit and the feature would silently do
  nothing.
- =work/=, =tmp/=, =.git/=, =.gate-cache/=, =*.fasl=, =*.db= and
  =.dart_tool/= are excluded: derived state.
- A project with a large generated tree adds it to =GATE_EXCLUDES=, e.g.
  =GATE_EXCLUDES := dart/build=.  Do not narrow =GATE_INPUTS_DEFAULT= to make
  a digest cheap: a narrower default was measured to miss a root-level test
  file, which is a false hit.
- A stamp value must be ONE WORD. Make splits `GATE_STAMPS_<gate>` into words
  before the recipe reaches the shell, so `flutter=Flutter 3.47.2 • channel …`
  arrives as five stamps (`flutter=Flutter`, `3.47.2`, `channel`, …) — silently,
  which is the dangerous part. Write a token, not a banner:
  `GATE_STAMPS_dump-index-check = flutter=$(shell $(FLUTTER) --version | head -1
  | cut -d' ' -f2)` gives `flutter=3.47.2`.
- Makefile-DEFINED settings are already in the digest (the Makefile is an input).
  `GATE_STAMP_ENVS` exists for what can be typed on the COMMAND LINE: `PKG`,
  `REPORT`, `EVAL`, `DYNAMIC_SPACE_SIZE`, and any selector a project's gates read
  (`GATE_STAMP_ENVS += RP_SCENES` plus `export RP_SCENES`). The rule: if it can be
  overridden on the command line and it changes what the gate examines or how it
  decides, it belongs in the digest.
- =capture-output= writes the RUN's timestamp into the log header.  A restored
  log keeps the original timestamp on purpose: it is that run's output.

Targets that *write* committed files (=demos-emit=, =scenes-emit=,
=generate-goldens=) must never be receipted: a skipped emitter is a stale
committed file with no symptom until a gate disagrees with the twin.

** Conditional Features

*** Binary Build (=BINARY_NAME=)

When =BINARY_NAME= is set, two additional targets become available:

- =make build= — Builds a standalone binary via =asdf:make= → =bin/<name>=
- =make install= — Copies =bin/<name>= to =$(INSTALL_DIR)=

Example:

#+begin_src makefile
BINARY_NAME := my-cli
include .cl-make/cl-project.mk
#+end_src

*** Build Info (=build-info.sexp=)

Every =make build= (and =make force-load=) regenerates a
=build-info.sexp= at the project root via the =build-info= target:

#+begin_src lisp
(:version "0.1.0" :git-sha "abc1234" :git-branch "main" :git-dirty "clean")
#+end_src

Lisp code can read this at load time (e.g. in a small =src/build-info.lisp=)
so the current git state is baked into the image at dump time. This is the
classic CL "version file" pattern — the file is regenerated on every build, so
=--version= always reports the exact commit the binary was built from.

Key variables:

- =BUILD_INFO_FILE= — output path (default: =<project>/build-info.sexp=)
- =BUILD_INFO_FORM= — the sexp written (default: version+git metadata;
  set to empty to disable)
- =PROJECT_VERSION= — semantic version, auto-extracted from the =.asd=
  =:version= (override if the =.asd= lives elsewhere)
- =BUILD_GIT_SHA= / =BUILD_GIT_SHA_FULL= / =BUILD_GIT_BRANCH= / =BUILD_GIT_DIRTY=
  — computed from the project repo at build time (override =GIT= for a
  custom binary)

Because the file is regenerated (and should never be committed), add
=build-info.sexp= to the project's =.gitignore= — otherwise it will always
show as an untracked file and the =dirty= flag will never be =clean=.

*** Golden File Generation (=GOLDEN_PACKAGE=)

When =GOLDEN_PACKAGE= names a package with =*update-goldens*= and
=*update-pixel-goldens*= specials, =make generate-goldens= becomes available.
Runs the test suite with both variables set to =T=.

Example:

#+begin_src makefile
GOLDEN_PACKAGE := stratodendron.test
include .cl-make/cl-project.mk
#+end_src

** Fresh Build System

=mk fresh-build= runs a fresh SBCL compilation of the entire project,
capturing all compiler conditions (errors, warnings, style-warnings, notes)
into a structured s-expression file under =<project>/tmp/fresh-build-<timestamp>.lisp=.

=mk summarize= parses the latest fresh-build output and prints a human-readable
summary: total condition counts, per-file heatmap, and samples per severity.

=mk build-report= combines both in one command.

** Adding Custom Targets

Project-specific targets go /after/ the =include= line.  You can use any of
the defined variables and macros:

#+begin_src makefile
PROJECT_SYSTEM := my-project
include .cl-make/cl-project.mk

# Fast demo with Quicklisp-only boot:
demo-my-feature: check-quicklisp
	$(SBCL_QL) --eval '(ql:quickload :my-project/demo/feature)' \
	           --eval '(my-project.demo.feature:run)'

# Custom test suite with output capture:
test-smoke: check-quicklisp
	$(call capture-output,test-smoke,$(SBCL_RUN) \
	  --eval '(ql:quickload :my-project/smoke-tests)' \
	  --eval '(my-project.smoke-tests:run)') ; \
	RC=$$?; \
	grep -E "Passed:|Failed:" $(OUTPUT_DIR)test-smoke-LATEST.txt | tail -1; \
	exit $$RC

# Custom clean-up:
nuke: clean
	rm -rf tmp/ node_modules/
#+end_src

** ~git-stack.sh~ — Batch Git Operations

Operates on all git repos under =repos/= plus the meta-repo itself.

#+begin_example
Usage: ./.cl-make/git-stack.sh <command> [args]

Commands:
  status          Show git status for all repos
  log [n]         Show last n commits (default: 5)

#+end_src

Scans Lisp source files for non-ASCII characters.  Defaults to =repos/*/src/=,

#+begin_src bash

#+end_src

Exit 0 = clean.  Non-zero = found unicode (printed with =file:line:char=).

** ~gate-receipt.sh~ — Incremental Gate Receipts

run= by =cl-project.mk= for every receipted gate; documented in
*Gate Receipts* above.  Useful by hand when a digest looks wrong:

#+begin_src bash
# the digest of a gate, and WHY (the manifest lists every input file)
./.cl-make/gate-receipt.sh digest test --root . --input . --input .cl-make \
  --siblings .. --sbcl sbcl --verbose

./.cl-make/gate-receipt.sh status --cache .gate-cache --verbose
./.cl-make/gate-receipt.sh clean  --cache .gate-cache --all
./.cl-make/gate-receipt.sh selftest     # 20 assertions, ~1s, no SBCL
#+end_src

A missed hit is almost always one of three things: an input that really did
change (the manifest names it — diff two manifests), a stamp that moves on its
own (=build-info.sexp= is excluded precisely because it does), or a
=CACHE_VERSION= bump.  =FORCE=1= and =cache-clean= are the escape hatches;
neither can make a red gate green.

* Design Rationale

** Why =.cl-make/= as a submodule?

Inspired by GrammaTech's =SEL= project (=github.com/GrammaTech/cl-make.git=).
A dot-prefixed directory signals "build infrastructure, not source."
The submodule pattern gives each sub-repo an explicit, version-pinned
dependency on the shared infrastructure.

** Why two SBCL commands (=SBCL_RUN= vs =SBCL_QL=)?

The ASDF source registry =:tree= scan over the parent directory discovers
sibling repos automatically — essential for projects with inter-repo
dependencies.  But the scan takes 10-15 seconds.  For demos, dev cycles,
and targets that just call =ql:quickload=, the lightweight =SBCL_QL= gives
1-2 second startup.  Best of both worlds.

** Why pipefail?

=.SHELLFLAGS := -o pipefail -c= ensures that when a command is piped
through =tee=, the exit code of the /first/ command is preserved, not
=tee='s exit code.  This lets =capture-output= and the =test= target
accurately report pass/fail status even when output is captured.

** Why output capture to ~/tmp/~?

Predictable, globally unique file paths (=/tmp/<project>-<target>-LATEST.txt=).
Never checked into git.  Easy to find (=ls /tmp/<project>-*=), easy to
clean (reboot or =rm=).  The =LATEST= suffix means each target has exactly
one historical output — no accumulation cruft.
